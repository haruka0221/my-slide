The Judgments Behind the Data

データ構築と判断

異なるデータベースのレコードを照合・同定する際には、 次の点を記録・検証する必要がある。

どの候補を採用したか。
何を根拠にその候補を選んだか。
その判断はどの程度正確か。
不確実な例や誤りを、 あとから確認できるか。

データ規模が大きくなるほど、 こうした判断過程を記録し、 評価できる形で残す必要がある。

GPTとJevにおける判定の設計

GPT：判定方針をpromptで与える

対象作品とWikidata候補を渡し、 作品として同一かを判断させる。 

Determine which Wikidata candidate, if any,
best represents the TARGET literary work.

• Judge work identity, not title similarity alone
• Author identity matters
• Prefer a work-level item over an edition,
  translation, or adaptation

Return:
MATCH / NO_MATCH / AMBIGUOUS
selected_qid
confidence
reason

　　　　　　　　　　　　　　　　　　GPT-5.6 Luna / frozen prompt v6

Jev：問いの形をあらかじめ選ぶ

・　Noul： Yes / Noを判定 → Yesの確率（0–1）
・　Choice： 複数候補から1つ選択 → 選択結果＋各候補の確率
・　Score： 段階評価 → スコア＋確率

* JevはMATCH / NO_MATCHを直接返さないため、 候補ありでは any_candidate_match ≥ 0.5 をMATCHとして暫定集計。 候補0件はNO_MATCHとして処理。 0.5は今回、結果確認のために後から置いた基準。

最終結果の不一致はどこで生じたか

候補生成段階での不一致
GPT 2件
Jev 2件
Wikidataには正解QIDが存在した（＝人間はMATCHと判断）が、 Pythonで作成した候補集合内に正解QIDが入らなかった。
→ 両モデルから見ると「正解候補なし NO_MATCH」
確率から最終判定への変換
Jev 4件
正解QIDは候補にあり、 Jevも正しい候補を選択。
ただし any_candidate_match が0.5未満だったためNO_MATCHとなった。
MATCH / NO_MATCHの判定
Jev 1件
Human goldではNO_MATCHだったが、 JevではMATCHと判定した。
候補生成はGPT / Jev共通の前処理

Pythonでタイトル・著者・タイトル類似度から候補を絞り、 judgeには小さな候補集合だけを渡した。 100作品で平均4.42候補、最大25候補。

不一致は、 候補から正しいQIDを選ぶ段階だけでなく、 候補生成や、Jevの確率を最終判定に変換する段階でも生じた。

同じ候補情報でも判定の設計で結果が分かれた

対象作品
Dyrendel
by Johan Bojer / 1921
候補 Q12714183
title：欠損   /   author：Johan Bojer   /   year：1921
description： “1921 novel by Johan Bojer”

GPT-v6 → NO_MATCH

実際の判断理由

"作者と年は一致するため候補としては plausible。 ただし、 Dyrendelと結びつけるタイトルその他の肯定的な証拠がない"

promptで明示していた基準

情報が欠けていて「矛盾がない」だけでは、MATCHの根拠にしない。
作者・年代が一致していても、タイトルなど作品同一性を示す情報が必要。

Jev → MATCH

個別の問いとして判定

この候補は同じ作品か？ → 0.64
候補内に対応する作品があるか？ → 0.68
最も妥当な候補は？ → Q12714183
　(これはDen siste vikingという別作品のQID)

タイトルは欠けている一方、 作者・年代・作品タイプは一致。 その一致を反映して、 0.5を超える確率を与えた。

この例では、モデルそのものだけでなく、 GPTに与えた判定基準と、Jevでの問いの分け方 が最終結果の違いに表れた。

今回の実験から見えたこと

LLM

MATCH / NO_MATCH、 対応するQID、判断理由まで まとめて出力できる。

向いている場面

判断理由を確認したい場合や、 例外的なケースを個別に検討したい場合。

Jev

判断をNoul / Choiceなどに分け、 確率や選択結果として取得できる。

向いている場面

同じ種類の判断を繰り返し、 確率を使って処理を分岐させたい場合。

モデル以外の設計も結果に影響する

今回の不一致には、 候補生成や入力メタデータの不足によるものもあった。 Jevではさらに、確率をMATCH / NO_MATCHに変換する基準によって最終結果が変わる。

「LLMかJevか」という二者択一というより、判断のどの部分をAIに任せ、どこをルールや人手で処理するかという違いとして考えられる。
